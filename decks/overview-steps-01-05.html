One branch per step — step-01 … step-05 — each merged to main through a pull request. Nobody commits straight to main: it costs nothing while you are alone in the repo, and it is the habit that keeps a team from standing on each other later.

Two applications, side by side — neither inside the other. Each owns its own Dockerfile at the root of its own folder; docker-compose.yml sits at the workspace root and wires them together. Add a README.md there with your name on it. 

fx-exchange/

From Step 4 on, the pipeline files move up a level. .github/workflows/ci.yml and cd.yml live at the true root of your fork — beside fx-exchange/, not inside it — because GitHub Actions only reads workflows from the repo root. Every step inside them then names working-directory: fx-exchange/fx-app-spring explicitly, because the Gradle build lives two levels down from there.

Docker Desktop must be running. If it won't install on your laptop, say so at stand-up now and pair with someone whose machine works — every task after the first builds on a running stack. Keep two terminals open all day: one for docker compose logs -f, one for everything else. The lessons live in the logs.

The steps

1 · Put it in a box

AM · ~65 min · deck: Containerisation / Dockerfiles

Why: "works on my machine" is a bug report, not a status.

Start a new repo, and no database needed — stop MySQL for this one. Lay the workspace out first (two sibling apps, README with your name), then write the Dockerfile in stages and run it after each: naive single-stage → publish a port → diagnose the whose localhost? failure (and deliberately not fix it) → multi-stage → prove the layer cache by touching a file → .dockerignore → override config with -e → volumes and bind mounts → the everyday ps/logs/exec/images commands.

Stuck? The container starting is not the app working — the pool is lazy, so /health is green while /api/rates is 500. Read the container log, not the HTTP body.
Checkpoint: /health UP · / 404 · /api/health/db DOWN · /api/rates 500 — running with no JDK, no Gradle and no MySQL. Multi-stage image smaller; rebuild leaves go-offline CACHED. The 10 rates arrive in Step 2.

2 · The whole stack in one file

AM · ~60 min · deck: Containerisation

Why: the app was portable, the database still wasn't.

A db service and an app service, wired by service name not localhost. Healthcheck + depends_on: condition:, named volume vs bind mount, .env and ${VAR:-default}, and the down / down -v experiment that explains why your seed edits "did nothing".

Stuck? 3307:3306 — left is your laptop, right is inside. Container-to-container traffic uses the right one.
Checkpoint: local MySQL stopped, docker compose up serves 10 rates; down -v && up re-seeds from scratch.

3 · A second app, and the port fight

PM · ~45 min · deck: Containerisation

Why: most containers you'll ever run were built by someone else.

fx-monitor is given complete — containerise it, add it to the stack, hit port is already allocated, and work out which of the two numbers caused it. nginx serves the page and proxies /api onward, so the browser stays same-origin and CORS never enters the picture.

Stuck? Container ports are private to each container; published host ports are shared across your whole machine. It is always the left-hand number.
Checkpoint: three services up · http://localhost:3000 renders the live table · the ACCEPTING toggle reads ON and rates tick every couple of seconds — fx-app-spring feeds itself, no second app required.

4 · The machine runs the tests (CI)

AM/PM · ~45 min · deck: CI / GitHub Actions

Why: a test only protects you if it runs without you remembering to run it.

Author .github/workflows/ci.yml at the repo root (working-directory: fx-exchange/fx-app-spring), triggered on push and pull_request, running ./gradlew build against your existing test suite — nothing new to write here. Then rig a PR with a deliberately failing assertion, watch CI go red, and turn on branch protection so red can't merge.

Stuck? "Required status checks" in branch protection is what turns a red X from a suggestion into a locked merge button. No protection rule → nothing is actually enforced.
Checkpoint: your Actions tab shows a red run followed by a green run; the rigged red PR is blocked by branch protection — the merge button won't go.

5 · From green build to blessed deploy (CD)

PM · ~45 min · deck: CI→CD

Why: shipping should be one click a human takes on purpose — not a thing that happens by accident.

Split the pipeline by trigger so nothing builds twice: narrow ci.yml to pull_request and add a build-only images matrix, then add cd.yml on push: [main]. Its jobs chain: build (verify) → publish (log in to ghcr.io, build, push sha-<short> and latest for both fx-app-spring and fx-monitor) → deploy (environment: staging, a required-reviewer gate; the deploy itself is a stand-in echo for now).

Stuck? ghcr package names must be lowercase. If github.repository_owner has capitals, the push 400s — lowercase it in the workflow.
Checkpoint: a merge to main runs cd.yml; fx-app-spring and fx-monitor both show up on ghcr with two tags — sha-<short> and latest; the deploy job waits for a reviewer before it runs.

GenAI closer — build the habit that saves you

~10 min

Have an assistant review your Dockerfile, then your ci.yml and cd.yml — and price every suggestion before taking one. Then ask it to "speed up CI", and see whether it reaches for a sleep in the port-fight step, or for dropping a test in the pipeline step, to get there faster.

Theory background

A container is a process, not a computer

No second operating system is booted. Your process runs on the same kernel as everything else, with its own view of the world: its own filesystem, its own process list, its own network interface. That is why it starts in milliseconds and why localhost means something different inside it.

Images are layers, and order is everything

Each instruction adds a read-only layer; a container adds one thin writable layer on top. Docker re-runs a layer only when the files it copies have changed — and every layer after it. Copy build.gradle and resolve dependencies before copying src, and a source edit rebuilds in seconds instead of minutes.

Two ports, two different jobs

-p 3000:80 — the left is a port on your laptop, a scarce machine-wide resource; the right is inside the container, private to it. Ten containers can all use port 80 internally. Only one can publish on host 3000. Every "port is already allocated" is about the left-hand number.

Compose networking: names, not addresses

Every service gets a DNS name equal to its service name, resolved on an internal network. fx-db:3306 works and doesn't care what IP the container happens to have. And "started" ≠ "ready": a healthcheck plus depends_on: condition: service_healthy is the difference between a reliable stack and one that works on the second try.

CI is a gate, not a chore

A pipeline that runs the suite on every push tells you when something broke. Branch protection — a required status check — is what turns that from information into enforcement: a red run doesn't just warn you, it locks the merge button. Green stops being an opinion and becomes a precondition.

CD ships; a human blesses

The CD pipeline builds the image, tags it sha-<short> so every deploy is traceable to an exact commit, and pushes it to the registry — all automatic. The deploy job then sits behind environment: staging with a required reviewer. Automation carries the change to the door; a person decides to open it. That gate is the difference between automation and abdication.

Extra challenges

Shrink the image

Try eclipse-temurin:21-jre-alpine, then a jlink-trimmed runtime. Record the sizes. Then find the cost: what changed about libc, DNS, or your JVM flags? A smaller number that breaks in production is not a win.

Run as a non-root user

Add a USER to the runtime stage and make the app still work — including the log volume. This is the single highest-value hardening step for a container, and the one most likely to break something quietly.

Add a smoke-test job that curls the running container

After cd.yml pushes the image, add a job that docker run -d that exact image, waits for /health, curls /api/rates and asserts it got 10, then tears it down. A green build and a container that won't start are not mutually exclusive — this catches the gap.

Add a CI status badge

Drop a ![CI](.../actions/workflows/ci.yml/badge.svg) badge into your fx-exchange/README.md. It's one line of Markdown, and it's the first thing a teammate — or a reviewer — checks before reading anything else.
